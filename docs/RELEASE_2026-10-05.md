## Scheduler diagnosis

The 05:41 UTC run on October 5 reported: "Last refresh 336 minutes ago; 4 in the
last 24h." The rolling cap, not minimum spacing, prevented it from refreshing
([run log](https://github.com/neilweitzel/xfeeds/actions/runs/37268920567)).

AbuseIPDB documents that APIv2 limits reset at 00:00 UTC, supporting a four-refresh
UTC-calendar-day cap rather than the rolling window
([FAQ](https://www.abuseipdb.com/faq.html)).
GitHub explicitly permits delayed or dropped scheduled jobs. Absence from the
run list does not identify the particular platform failure, and another GitHub
schedule is not an independent backup
([GitHub documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)).

The final implementation uses hourly opportunities with **5h30 minimum spacing**,
not the initially proposed four hours. Four-hour spacing plus an hourly trigger
would front-load four daily attempts and force a long overnight gap. The half-hour
tolerance admits the October 5 replay without abandoning the six-hour target.
Attempt reservations also account for failed pipeline runs. The owner explicitly
declined an outside backup on October 5; none was created.
